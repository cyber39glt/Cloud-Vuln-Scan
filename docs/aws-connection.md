# AWS Connection

How the platform gets **temporary, read-only** access to a client's AWS account,
how a client grants it, and how to test it against your own sandbox.
Decisions: [ADR 0005](decisions/0005-cloud-access-model.md),
[ADR 0002](decisions/0002-read-only-security-boundary.md),
[ADR 0014](decisions/0014-aws-connector-and-dev-identity.md).

## How it works

```
Platform identity (SubtleTech)                 Client AWS account
        │                                              │
        │ 1. sts:AssumeRole(role ARN, ExternalId) ───► │ Role "SubtleTechSecurityAssessment"
        │                                              │  • trusts ONLY the platform identity
        │ 2. temporary keys (≤ 1 hour) ◄────────────── │  • requires the ExternalId
        │                                              │  • SecurityAudit + ViewOnlyAccess
        │ 3. Describe/List/Get calls only ───────────► │  • explicit Deny on data and secrets
```

| Term | Meaning |
|---|---|
| **boto3 / botocore** | AWS's official Python SDK. Each call such as `ec2.describe_security_groups()` is an HTTPS request to one AWS API operation (`ec2:DescribeSecurityGroups`). |
| **STS AssumeRole** | AWS Security Token Service operation that exchanges one identity for **temporary** credentials of a role. |
| **ExternalId** | A unique value per client connection that the role requires. Prevents the "confused deputy" problem: someone who knows the role name cannot use the platform to access it. Generated by the platform, never chosen by the client. |
| **CloudFormation** | AWS "infrastructure from a file". The client deploys our template and AWS creates the role exactly as written. |

### The two read-only layers

1. **In the client account** (`infra/aws/client-onboarding-role.yaml`): read-only
   AWS-managed policies plus an explicit **Deny** on reading data and secrets (S3 object
   contents, Secrets Manager values, SSM parameters, KMS decrypt, database items, log
   contents, EC2 Windows passwords and console output, etc.). A Deny overrides any Allow,
   even if more permissions are attached to the role later.
2. **In the platform** (`backend/app/providers/aws/guard.py`): every boto3 session is
   guarded. Before a request is even built, the operation is checked against an
   **allowlist** derived from the enabled rules' declared permissions. Anything else,
   including any write, raises `ReadOnlyViolation` and nothing is sent.
   - The platform's own identity may only call `sts:GetCallerIdentity` and `sts:AssumeRole`.
   - Inside client accounts only `Describe*`/`List*`/`Get*` operations can be allowed;
     this is enforced in code and by tests.

### What the client sees

Every session is named `SubtleTech-assessment-<random>`. In **their own CloudTrail**,
clients can see every call made during the assessment.

### What the platform stores

The client's **account ID** and **ExternalId** only. Neither grants access without the
platform's own identity. Temporary credentials live in memory for at most one hour and
are never written to disk, logs or the database.

## Client onboarding (what a client does)

1. The consultant gives the client: the template file, the **platform identity ARN** and
   the **ExternalId** for that client (`python -m app.cli aws external-id`).
2. The client signs in to their AWS console → **CloudFormation** → **Create stack** →
   **With new resources** → **Upload a template file** → selects
   `client-onboarding-role.yaml`.
3. Stack name: `SubtleTech-security-assessment`. Parameters: paste the ARN and ExternalId;
   keep the default role name.
4. Tick "I acknowledge that AWS CloudFormation might create IAM resources" → **Submit**.
5. When the stack shows `CREATE_COMPLETE`, the client sends their **account ID**.
6. To revoke access at any time: delete the stack.

## Testing against your sandbox (one account playing both sides)

Do this after creating your sandbox account (admin user with MFA, budget alert).
Everything below is free.

### A. Create the platform identity (plays "SubtleTech")

1. AWS console → **IAM** → **Policies** → **Create policy** → **JSON** tab, paste:

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Effect": "Allow",
         "Action": "sts:AssumeRole",
         "Resource": "arn:aws:iam::*:role/SubtleTechSecurityAssessment"
       }
     ]
   }
   ```
   Name it `SubtleTechScannerAssumeOnly` → **Create policy**.
2. **IAM** → **Users** → **Create user** → name `subtletech-scanner-dev`. Do **not** give
   console access. **Attach policies directly** → tick `SubtleTechScannerAssumeOnly`
   only → **Create user**.
3. Open the user → copy its **ARN** (e.g. `arn:aws:iam::<your-account>:user/subtletech-scanner-dev`).
4. **Security credentials** tab → **Create access key** → choose
   **Application running outside AWS** → create → copy both values **once**.
5. Put them in your local `.env` (never anywhere else):
   ```
   AWS_ACCESS_KEY_ID=AKIA...
   AWS_SECRET_ACCESS_KEY=...
   ```

### B. Deploy the client role (plays "the client")

1. Generate an ExternalId:
   ```powershell
   .\scripts\dev.ps1 aws external-id
   ```
2. Follow **Client onboarding** above in your sandbox, using the ARN from A.3 and the
   ExternalId from B.1.

### C. Validate

```powershell
.\scripts\dev.ps1 aws validate --account-id <your-12-digit-account-id> --external-id <id>
```

Expected:
```
[ OK ] Platform AWS identity  arn:aws:iam::...:user/subtletech-scanner-dev
[ OK ] Assume assessment role  arn:aws:iam::...:role/SubtleTechSecurityAssessment
[ OK ] Expected account  ...
[ OK ] Permission cloudtrail:DescribeTrails
[SKIP] Permission cloudtrail:GetTrailStatus  Verified during collection.
[ OK ] Permission ec2:DescribeRegions
[ OK ] Permission ec2:DescribeSecurityGroups
[ OK ] Read-only guard  Write operations are blocked locally.

Connection is ready.
```

Try a wrong ExternalId: "Assume assessment role" fails with a plain-language hint.

### Housekeeping

- The access key is for development only. Rotate it (create new, delete old) every
  90 days, and delete it if it may have leaked. Gitleaks scans for committed keys.
- The ExternalId on the command line appears in your shell history. That is acceptable
  for development; the web UI (later) will not need it on a command line.

## Troubleshooting

| Message | Usual cause |
|---|---|
| The platform has no AWS identity configured | `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` missing in `.env`, or containers not restarted |
| The platform's AWS credentials are not valid | Access key deleted, deactivated or mistyped |
| AWS denied the request (assume role) | Wrong ExternalId, wrong account ID, stack not deployed, or the role trusts a different ARN |
| Expected account … got … | The account ID typed does not match where the role lives |
| Permission … failed | The role is missing a read permission (stack modified?) |
